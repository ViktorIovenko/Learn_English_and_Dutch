# Codex workflow

Перед любой работой:

1. Выполни `git status --short` и прочитай этот файл.
2. Сначала запроси `.codex/project_kb.sqlite` через `python tools/project_kb.py files-for "<задача>"` или другую точечную CLI-команду.
3. Открывай только основные файлы из результата; зависимости и consumers — только по найденным импортам/вызовам.
4. Если индекса недостаточно, используй `rg` только по названным файлам/каталогам. Полный скан допустим лишь при изменении архитектуры или самой базы знаний.

## Границы

- Получай список исходников через `git ls-files`; не обходи рекурсивно весь репозиторий/диск.
- Не открывай `.env`, SQLite data, аудио, изображения, APK/AAB, generated/cache/build/log directories.
- Не сохраняй секреты, пользовательские строки БД и production-логи в документацию или индекс.
- Local и production не считаются одинаковыми без проверки commit SHA; если на production нет `.git`, сравнивай только метаданные/хэши и явно отмечай ограничение.
- Перед любым серверным действием проверь production Git state. Не запускай второй Telegram polling, не перезапускай сервисы для проверки кода, не деплой без прямого требования.
- Не изменяй несвязанные файлы и не исправляй найденный drift автоматически.

## После изменения

1. Выполни минимальную профильную проверку.
2. Обнови только затронутые файлы: `python tools/project_kb.py update --files ...`; полный `update` нужен для проверки удалений/набора файлов.
3. Отдельно реши, требуется ли production-проверка/деплой.
4. В отчёте раздели local и production; укажи проверки и restart.

Полный порядок: status → AGENTS → KB query → предложенные файлы → связанные API/таблицы/клиенты → минимальное изменение → точечная проверка → incremental update → отдельное решение о production → отчёт.
